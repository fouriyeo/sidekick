# 文档树与懒加载规范

> 目标：AI 和新人都能**只读需要的那一页**，不被整棵文档树淹没。
> 文档不是知识堆，是路由；索引负责“带路”，叶子负责“说清一件事”。

## 1. 结构规则

- 根入口唯一：`docs/INDEX.md`。
- 每个分支目录必须有 `INDEX.md`；索引只做三件事：概览、路由、维护提示。
- 目录按“问题域”分，不按文件类型分：
  - `product/` 为什么、给谁、做什么、怎么衡量。
  - `standards/` 全项目规则。
  - `prd/` 功能需求，按功能再分目录。
  - `engineering/` 技术方案。
- 现有扁平文档（`architecture.md`、`frontend-architecture.md` 等）保留原名，作为“基础文档”挂在根索引；不要为了整齐大搬家，避免链接失效。
- 叶子文档只讲一个主题；标题就是结论，第一段就是摘要。

## 2. Frontmatter 元数据

新分支下的 Markdown 必须以 YAML frontmatter 开头：

```yaml
---
doc: prd/pet/PRD        # 稳定 ID = 相对 docs/ 的路径去掉 .md
title: 情绪宠物 PRD
status: draft           # draft | active | frozen | deprecated
updated: 2026-10-31
load: on-demand         # always 只给根索引；其它一律 on-demand
owner: product          # product | design | engineering | qa
children: []            # 仅索引使用
related: []             # 可选，最多 4 个
---
```

规则：

- `doc` 一旦发布不改名；改名视为废弃 + 新建。
- `status`：`draft` 未评审；`active` 生效；`frozen` 本期不再改；`deprecated` 有替代文档。
- `updated` 只在内容有实质变化时更新，不因格式化更新。
- 索引页的 `children` 必须与实际链接一致。
- 现有基础文档没有 frontmatter，不强制补；新文档必须写。

## 3. 体量预算

| 类型 | 上限 | 超了怎么办 |
| --- | --- | --- |
| 根索引 | 140 行 | 合并/删减路由项 |
| 分支索引 | 120 行 | 拆子分支 |
| 规范/工程叶子 | 300 行 | 按“规则/方案/测试”拆 |
| PRD | 360 行 | 把体验细节移到 SPEC，验收移到 ACCEPTANCE |
| SPEC | 300 行 | 按“布局/状态机/文案”拆 |
| ACCEPTANCE | 200 行 | 按功能模块拆 |

说明：PRD 上限放宽到 360，是因为固定包含背景、规则、质量门、排期与验收摘要；根索引 140 是因为要容纳任务路由与目录树。两者仍然要求“按节读”，不是鼓励整篇灌入。旧的基础文档（无 frontmatter）不套用新上限，避免为了行数大搬家。

体量用 S/M/L 标注：S < 80 行，M 80–200，L > 200。L 文档必须在索引里写“读哪节”。

## 4. 懒加载阅读协议（AI 必读）

1. 始终加载：`AGENTS.md` + `docs/INDEX.md`。
2. 从根索引的“按任务选分支”里选 **1 个**分支，读它的 `INDEX.md`。
3. 在分支索引里选 **最多 2 篇**叶子；先读摘要/表格，不够再读具体章节。
4. 禁止：
   - 一次性 `cat docs/**/*.md`；
   - 为了“了解背景”读完整分支；
   - 把整篇 PRD 贴进上下文却不说明用哪节。
5. 需要跨分支时，最多再开 1 个分支索引；仍不够就向用户确认，不要全量扫描。
6. 回答时写清依据路径；提交代码时在 PR/说明里列出同步过的文档。
7. 读完发现索引缺失、链接错误或内容过期，把修索引当作本次任务的一部分。

## 5. 写作规则

- **先结论后解释**：第一段回答“这篇解决什么问题”。
- **一条规则一个位置**：同一条事实只写一处，其它地方链接。
- **可执行**：规则要能被评审或测试验证；不写“尽量”“适当”“视情况”。
- **不写易失信息**：IP、PID、临时路径、当前版本号（以 lockfile 为准）。
- **表格优先**：规则、状态、异常、验收用表格；散文只用于背景和取舍。
- **中文为主**：术语首次出现给英文/代码名；命令和字段保持原文。
- **不复制模板**：PRD/SPEC/AC 分工见 [product.md](./product.md)，不要三份文档写同一段话。

## 6. 新增文档流程

1. 判断归属：产品 / 规范 / PRD / 工程；只影响一个功能就放该功能目录。
2. 复制 frontmatter，填 `doc/status/updated/load/owner`。
3. 写“这篇解决什么 + 读者 + 不包含什么”。
4. 在父索引的“读哪篇”表格里加一行，写清“何时读”。
5. 跑 `node scripts/check-docs.mjs`，修链接和行数警告。
6. 如果是重大决策，追加 [decisions.md](../decisions.md)。

## 7. 修改与废弃

- 修改事实：先改“唯一归属”文档（见 [INDEX.md](../INDEX.md#5-事实的唯一归属)），再检查引用。
- 修改规则：同步检查 PRD/SPEC/AC 是否冲突；冲突就更新版本号并写变更说明。
- 废弃：`status: deprecated`，在标题下写“替代文档”，保留至少一个版本周期。
- 删除：只有确认无引用、且内容已合并后才删除；先跑检查脚本。

## 8. 索引怎么写

每个分支索引固定四块：

1. 一句话：这个分支回答什么问题。
2. “读哪篇”表：问题 → 文档 → 体量/读哪节。
3. 当前结论/一页摘要：只放最关键的 5–10 行。
4. 维护规则：什么时候更新、和谁联动。

不要在索引里展开细节；索引超过 120 行就是信号：该拆了。

## 9. 机器检查

```bash
node scripts/check-docs.mjs
```

检查项：

- 每个分支目录是否有 `INDEX.md`；
- 新分支文档是否有必需 frontmatter；
- 相对链接是否存在（跳过 http、锚点、代码块）；
- 叶子是否超过 300 行（PRD 320）；
- 输出树形结构和体量，方便人工巡检。

检查失败不提交；警告可以在 PR 里说明原因。

## 10. 反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 一份大 PRD 写 800 行 | AI 每次全量读，上下文爆炸 | 拆 PRD / SPEC / AC |
| 规范里写实现细节 | 代码一改文档就废 | 实现进 `engineering/` |
| 索引里复制正文 | 两处不同步 | 索引只放摘要和链接 |
| 每个功能都新建一套规范 | 规则冲突 | 全局规则进 `standards/` |
| 文档没有 owner/status | 不知道能不能信 | frontmatter 必填 |
| 用“等/其他情况”收尾 | 无法验收 | 穷举规则和异常 |
