# 产品与 PRD 规范

> 目标：需求能被评审、被拆解、被验收；PRD 只写“做什么”，不写“怎么做”。
> 工具：可用 `product-management:PRD生成` 技能起草，但本文件与 PRD 正文是项目事实源。

## 1. 三层文档分工

| 文档 | 回答 | 读者 | 不该写 |
| --- | --- | --- | --- |
| PRD | 为什么做、给谁、做什么、规则、优先级、成功标准 | 产品/评审/所有人 | 布局坐标、颜色、技术选型 |
| SPEC | 长什么样、怎么动、状态怎么变、文案是什么 | 设计/前端/测试 | 商业目标、排期、协议字段 |
| ACCEPTANCE | 怎么证明做对了 | 测试/开发/评审 | 背景故事、设计理念 |

实现方案（协议、音频链路、Rive 输入、性能预算）放 `engineering/`。三层文档用链接互指，不复制。

## 2. 需求来源与证据

每条需求标注来源，至少一个：

- 用户反馈 / 自用痛点；
- 数据分析（本期主要是本地事件与试用记录）；
- 竞品/参考产品；
- 技术约束（例如 Android 后台限制）；
- 产品判断（明确写“判断”，不要伪装成数据）。

禁止：

- “用户可能需要”但没有来源；
- 编造 DAU、转化率、市场规模；
- 用“行业最佳实践”代替具体理由。

没有数据的目标值标 `[假设]`，并写验证方法。

## 3. 优先级

| 级别 | 定义 | 规则 |
| --- | --- | --- |
| P0 | 本期必须上线，缺了功能不成立 | 每个功能 ≤ 5 个 P0 模块 |
| P1 | 强烈建议，P0 稳定后做 | 不阻塞本期发布 |
| P2 | 锦上添花/未来 | 只记录，不排期 |

P0 判定三问：

1. 没有它，用户能不能完成核心任务？
2. 没有它，产品原则是否被破坏？
3. 它是否可以用更小的 P0 替代？

三问都否，降级。

## 4. PRD 模板

```markdown
# PRD：{功能}
版本 / 日期 / 状态 / 平台 / 关联文档

## 0. 一页摘要
## 1. 背景与目标
### 1.1 背景（为什么现在、不做会怎样）
### 1.2 目标用户（具体角色 + 场景，不写“所有用户”）
### 1.3 目标与成功指标（SMART，无数据标 [假设]）
## 2. 需求概述（30 字内）
## 3. 功能详细设计
每个模块：描述 / 用户故事 / 优先级 / 业务规则（穷举）/ 交互流程 / 异常处理
## 4. 非功能需求（性能/隐私/兼容/无障碍）
## 5. 数据需求（本地事件，不含 PII）
## 6. 验收标准（核心 Given-When-Then，详细放 ACCEPTANCE）
## 7. 排期建议（开发/测试/联调，标 [估算]）
## 8. 风险与依赖
## 9. 开放问题
## 10. 质量自检（10 项）
```

## 5. 质量门（10 项）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| 1 | 背景不空泛 | 回答“为什么现在做、不做会怎样” |
| 2 | 目标可量化 | 至少一个数字指标，或明确的试用验证方法 |
| 3 | 用户具体 | 有角色、场景、痛点；不出现“所有用户” |
| 4 | 规则穷举 | 无“等/其他情况/视情况”；边界值写清 |
| 5 | 异常覆盖 | 每个 P0 模块至少 2 个异常场景 |
| 6 | 验收可测 | Given-When-Then，能直接写成测试 |
| 7 | 数据完整 | 核心路径有事件；无 PII/原始音频/全文 |
| 8 | 无技术方案 | 不指定框架、数据库、协议字段 |
| 9 | 优先级明确 | 每个模块标 P0/P1/P2 |
| 10 | 排期有依据 | 含开发、测试、联调；标估算与依赖 |

评审时逐项打勾；不通过就退回，不在评论里“口头通过”。

## 6. 业务规则写法

- 触发条件：什么情况下生效。
- 处理逻辑：按顺序写 1/2/3，不跳步。
- 边界值：最短、最长、为空、重复、超限。
- 优先级：多个规则冲突时谁优先。
- 用户可见结果：成功/失败分别看到什么。
- 不可见结果：保存什么、丢弃什么、记录什么。

反例：`按住说话，松开发送。`
正例：`按下 ≥300ms 进入倾听；释放时若在取消区则丢弃，否则发送；<300ms 视为误触，不发送。`

## 7. 需求变更

- 版本号：`v0.x` 草稿；评审通过 `v1.0`；范围变化 `v1.1`，并写变更记录。
- 任何 P0 增删：更新 PRD、SPEC、ACCEPTANCE 三处相关段落，并追加 [decisions.md](../decisions.md)。
- 不改历史结论；在决策记录里写新日期和原因。
- 变更后重跑质量门和相关 AC。

## 8. 文案与语言

- 中文优先，短句，直白；不用“赋能/闭环/抓手”。
- 宠物文案：温柔、克制、不撒娇过度、不制造愧疚。
- 错误文案：说明发生了什么 + 下一步怎么做；不指责用户。
- 术语首次出现给英文/代码名，例如“支架模式（docked）”。

## 9. 评审角色

| 角色 | 看什么 |
| --- | --- |
| 产品（用户） | 价值、范围、优先级、文案 |
| 设计/前端 | 可行性、状态、动效、性能 |
| 测试 | 规则是否可测、异常是否覆盖 |
| AI 评审代理 | 10 项质量门、与规范冲突、遗漏角色 |

可用子代理：`sidekick-prd-reviewer`。它只评审，不改文档；结论写“阻塞/建议/通过”。

## 10. PRD 反模式

| 反模式 | 表现 | 纠正 |
| --- | --- | --- |
| 需求镀金 | 一期 30 个功能点 | 砍到 3–5 个 P0 |
| 伪需求 | “用户可能想要” | 标来源或删掉 |
| 交互越界 | 写按钮颜色、坐标 | 移到 SPEC |
| 技术越界 | 指定 Redis/协议字段 | 移到 engineering |
| 规则黑洞 | “按业务规则处理” | 穷举触发/处理/边界 |
| 指标造假 | 编造行业数据 | 标 `[假设]` + 验证方法 |
| 无异常 | 只写 happy path | 每个模块补 2 个异常 |
